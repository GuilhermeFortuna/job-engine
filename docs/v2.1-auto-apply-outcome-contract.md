## 1. Locked owner outcome

V2.1 is a visible desktop auto-apply product for jobs the owner explicitly
selects. For a supported `FULL_AUTO` run, one authorization at creation covers
verified form completion, intermediate navigation, résumé upload, final-submit
activation, and receipt reconciliation. Routine success has no second review or
release click. Human intervention is reserved for genuine exceptions.

The following outcomes are indivisible acceptance requirements:

1. The desktop UI always exposes an **Applications** destination.
2. Every job with an application URL displays exactly one understandable state:
   **Auto apply**, **Apply with assistance**, or **Automation unavailable** with
   a reason. A failed capability check never silently removes the feature.
3. The owner selects the exact job or jobs and a registered résumé, chooses the
   mode, and gives one explicit authorization when creating a `FULL_AUTO` run.
4. A supported `FULL_AUTO` run fills authorized fields, uploads the
   checksum-verified résumé, advances intermediate steps, activates final submit,
   and reconciles a receipt without a second routine click.
5. Missing or sensitive answers, low confidence, authentication, CAPTCHA,
   validation failures, unsupported required controls, platform drift, and
   ambiguous submission pause or stop truthfully.
6. The product never autonomously selects jobs, fabricates applicant facts,
   captures credentials, bypasses CAPTCHA or access controls, or blindly retries
   after a submission attempt.
7. Applications exposes readiness, queued/running/needs-attention/terminal state,
   mode, selected résumé, audit progress, and receipt or uncertainty.
8. Ordinary browser use remains safe and explains that automation requires the
   desktop runtime.
9. AI is a bounded, deterministic-policy-first answer provider for permitted
   narrative fields. It never selects jobs, controls the browser, answers
   sensitive/legal facts, or authorizes submission from model self-confidence.
   Local development and Gemini production use the same schema and evidence
   contract and fail closed.
10. The production automation surface is the Chromium `WebContentsView` embedded
    in Job Engine. Coverage begins with generic HTML, Greenhouse, and Lever and
    evaluates Ashby, SmartRecruiters, Workday, and every provider in the frozen
    catalog inventory. Unsupported pages remain visible with an exact reason;
    universal coverage is never claimed without evidence.

## 3. Visible product and capability contract

### Routes and destinations

- The global desktop navigation exposes **Jobs** and **Applications**.
- `/applications` is the persistent readiness, queue, attention, and history
  destination.
- `/applications/settings` manages applicant-profile readiness, registered
  résumés, default résumé selection, and reusable answers through the existing
  backend APIs.
- `/applications/{run_id}/workspace` remains the visible embedded-page,
  exception, progress, and receipt workspace.

The same routes may render in an ordinary browser, but automation controls must
be disabled with an explanation that the desktop runtime is required. Safe
external application links remain available.

### Per-job action state

Every job with an application URL resolves to exactly one state:

| State | Meaning | Owner action |
| --- | --- | --- |
| **Auto apply** | Desktop runtime is available, readiness is complete, and the provider/form capability permits `FULL_AUTO` | Select job(s), résumé, `full_auto`, review the authorization summary, and authorize once |
| **Apply with assistance** | The visible embedded workflow is usable but full-auto is not eligible | Select the job and résumé and explicitly create `semi_auto_pause_before_submit` |
| **Automation unavailable** | URL, runtime, readiness, provider, form, policy, or safety requirements prevent automation | Display the exact reason and a safe external fallback where available |

Capability truth comes from typed backend/desktop projections. React must not
duplicate adapter, policy, authorization, or submission-eligibility rules.

## 4. Run creation and authorization interface

`POST /api/v1/application-runs` remains the creation endpoint. The V2.1 request
contract is:

```json
{
  "job_group_ids": ["<explicitly-selected-uuid>"],
  "resume_id": "<registered-resume-id>",
  "automation_mode": "full_auto",
  "owner_confirmation": "Authorize automatic submission for these selected jobs"
}
```

- `job_group_ids` contains only the jobs shown in the authorization summary.
- `resume_id` identifies an already registered résumé; the run freezes its
  checksum and applicant/profile/answer-bank versions.
- `automation_mode` is required and is exactly `full_auto` or
  `semi_auto_pause_before_submit`. It has no default.
- `owner_confirmation` is required only for `full_auto` and must exactly equal
  `Authorize automatic submission for these selected jobs`. Missing or altered
  text returns `422` and creates no run.
- The backend records a server-generated
  `automatic_submission_authorized_at` timestamp for every full-auto run. Owner
  and runner read models expose that timestamp and a derived authorization
  boolean; no client may manufacture or infer authorization.
- Semi-auto creation does not accept or imply full-auto authorization.

Duplicate detection and explicit duplicate override remain separate from
full-auto authorization. Authorizing a run does not authorize a duplicate or a
different job, résumé, profile snapshot, or answer-bank snapshot.

## 5. Runtime, state, and exception contract

The durable statuses remain `queued`, `claimed`, `running`, `needs_input`,
`paused_auth`, `failed_retryable`, `failed_final`, `submission_unknown`,
`submitted`, and `cancelled`. The monotonic checkpoints remain
`form_discovered`, `profile_filled`, `questions_answered`, `resume_attached`,
`submit_armed`, `submitting`, and `submitted`.

For both modes, the production coordinator must:

1. Target-claim only a run selected or explicitly resumed by the owner.
2. Validate mode and, for full-auto, frozen backend authorization before page
   mutation.
3. Resolve the adapter against the currently visible `WebContentsView`, observe
   fields, request backend answer decisions, fill only authorized values, and
   verify the rendered result.
4. Fetch the single-use résumé grant, verify the advertised and actual SHA-256,
   attach it through the isolated-world transport, and remove temporary bytes.
5. Advance intermediate controls only while the lease is valid and no blocking
   exception exists.
6. At `submit_armed`, either wait for `release-submit` in semi-auto or proceed
   from frozen authorization in full-auto.
7. Record `submitting` immediately before one site-submit activation, then
   reconcile `submitted`, `submission_unknown`, or a truthful failure with
   redacted evidence.

`POST /api/v1/application-runs/{run_id}/release-submit` remains exclusive to a
semi-auto run at `submit_armed`; it rejects `full_auto`. A valid full-auto run
does not call this endpoint during routine success.

The following conditions block automatic progress and surface a named,
actionable state: missing required profile or answer data, sensitive/legal or
demographic facts without exact owner-authored authority, low-confidence or
invalid generated output, authentication, CAPTCHA, validation errors,
unsupported required controls, adapter/platform drift, lost lease, runtime or
network failure, and renderer/desktop interruption. Resumption must continue
from durable state without repeating a submit activation.

Once `submit_attempted_at` is set or the `submitting` checkpoint is recorded,
the run cannot automatically retry the final activation. A missing or ambiguous
confirmation becomes terminal `submission_unknown`; only receipt-backed
reconciliation may produce `submitted`.

## 6. Answer-provider boundary

The runner sends normalized observations to
`POST /api/v1/runner/runs/{run_id}/answer-decisions`; it never proposes values or
assigns confidence. The backend owns the following order:

1. Validate runner secret, lease, run identity, frozen résumé/profile/answer-bank
   versions, job evidence, and policy snapshot.
2. Apply exact owner resolutions, approved reusable answers, verified profile
   facts, prohibited/sensitive rules, and optional-decline rules before any
   provider call.
3. Offer only permitted narrative fields to an `AnswerProvider`.
4. Validate one strict structured result schema, every evidence identifier,
   control/length constraints, privacy state, provider/model/prompt revision,
   evaluation acceptance, and run authorization.
5. Derive `AUTO_FILL_AND_SUBMIT` on the server only when all gates pass;
   otherwise return `AUTO_FILL`, `REVIEW_REQUIRED`, `DECLINE_OPTIONAL`, or
   `ABSTAIN` as policy requires.

Local development uses a loopback OpenAI-compatible endpoint. Gemini uses a
backend-only API key and may receive real applicant evidence only after the
exact paid-project privacy attestation is owner-accepted. Both providers use
the same schema/evidence policy. Provider-reported confidence, prose, or
self-citation never authorizes submission, and AI never selects jobs, navigates,
clicks controls, uploads files, releases runs, or activates submit.

## 7. Coverage and evidence contract

Coverage is measured against a frozen inventory of application URLs from every
approved job source. Each URL is classified by downstream provider and one
support tier: `AUTO_SUPPORTED`, `ASSISTED_SUPPORTED`, or `UNSUPPORTED`, with a
machine-readable reason and evidence revision.

- Generic accessible standard forms, Greenhouse, and Lever are the starting
  implementation baseline, not automatic production claims.
- Ashby, SmartRecruiters, Workday, and every additional inventoried provider
  receive an explicit, evidence-backed decision.
- The coverage numerator counts only inventory URLs represented by a family
  proven through the compiled production Electron entrypoint. The denominator
  and every exclusion are published with the result.
- Standard-form acceptance requires all committed standard-form scenarios and
  at least 95% of eligible inventory URLs to be represented by proven
  auto-supported families.
- Authentication, CAPTCHA, nonstandard controls, provider restrictions, and
  drift remain visible assisted/manual exceptions and are not disguised as
  successful coverage.

Unit, jsdom, mocked bridge, and fixture-driver tests are supporting evidence.
Production acceptance additionally requires the compiled Electron main
entrypoint, real API and disposable PostgreSQL, the visible embedded surface,
backend events/receipt, and owner-visible walkthrough evidence against one
named commit.
